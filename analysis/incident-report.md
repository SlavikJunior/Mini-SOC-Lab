# Учебный отчёт об инциденте

## Статус

**Симуляция на синтетических данных.** Ни один вывод в этом документе не относится к реальной организации или реальному инциденту.

## Краткое резюме

В учебном наборе событий наблюдаются повторяющиеся неудачные попытки входа с одного адреса, после которых появляется успешный вход с того же адреса. Затем фиксируются запуск PowerShell с ключом `-EncodedCommand`, DNS-запрос и исходящее сетевое соединение. Эта последовательность требует проверки как потенциально подозрительная, но сама по себе не доказывает компрометацию.

## Временная шкала

| Время UTC | Источник | Событие | Интерпретация |
|---|---|---|---|
| 09:02:11–09:02:26 | Windows Security, 4625 | Три неудачных входа с `198.51.100.23` | Возможный перебор пароля; возможны и ошибки пользователя |
| 09:03:02 | Windows Security, 4624 | Успешный вход с того же адреса | Требует проверки учётной записи и типа входа |
| 09:04:18 | Sysmon, Event ID 1 | PowerShell с `-EncodedCommand` | Подозрительный признак, но не доказательство вредоносности |
| 09:05:30 | Sysmon, Event ID 22 | DNS-запрос `update-check.example.test` | Проверить домен и связанный процесс; имя в наборе демонстрационное |
| 09:07:44 | Windows Security, 4688 | `whoami.exe /all` | Может использоваться для изучения контекста привилегий; нужен контекст родительского процесса |
| 09:09:12 | Sysmon, Event ID 3 | Соединение на `203.0.113.77:443` | Проверить процесс, назначение и ожидаемость соединения |

Адреса `192.0.2.0/24`, `198.51.100.0/24` и `203.0.113.0/24` зарезервированы для документации и примеров. Домен `.test` также демонстрационный.

## Предполагаемая гипотеза

Возможная гипотеза для проверки: серия неудачных входов могла предшествовать доступу к учётной записи, после чего пользовательский контекст запускал PowerShell и инициировал DNS- и сетевую активность. Синтетические данные специально собраны так, чтобы показать ход первичного расследования; они не моделируют все доказательства реальной атаки.

## Что нужно проверить аналитику

1. Подтвердить, относится ли успешный вход к той же учётной записи и тому же источнику, что и неудачные попытки.
2. Проверить тип входа, временной пояс, доступность MFA и обычное поведение учётной записи.
3. Изучить родительский процесс PowerShell, полный command line и происхождение запущенного файла.
4. Проверить связанные Sysmon события, DNS-ответ, процесс-владелец соединения и соответствующий сетевой трафик.
5. Сопоставить события на других хостах и проверить, не являются ли действия частью разрешённого администрирования.

## Рекомендации

- Проверить учётную запись и при подтверждении подозрительного доступа сменить пароль, отозвать сессии/токены и проверить MFA.
- Проверить хост на дополнительные признаки компрометации и изолировать его только по утверждённой процедуре реагирования.
- Сохранить необходимые журналы и артефакты для дальнейшего анализа.
- Рассмотреть ограничение числа попыток входа, блокировку/оповещение по аномальным входам и централизованный сбор событий.
- Не блокировать адреса и не удалять файлы только на основании одного срабатывания; подтвердить вывод дополнительными данными.

## Ограничения

- Использован синтетический JSONL, а не исходные EVTX-файлы.
- В репозитории нет настоящего PCAP; сетевой анализ описан как следующий этап лабораторной работы.
- Детекторы являются демонстрационными эвристиками; требуется тестирование на чистых и подозрительных примерах.
