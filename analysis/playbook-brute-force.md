# Playbook: Brute Force → потенциальная компрометация учётной записи

> Учебный runbook репозитория Mini SOC Lab. Синтетический сценарий; процедуры
> рассчитаны на использование как шаблон для реальных инструкций реагирования.
> Прямое попадание в задачу «актуализация инструкций и процедур реагирования».

## 1. Триггер

Playbook включают детекции:

| Детекция | Severity | MITRE |
|---|---|---|
| `repeated_failed_logons` / `linux_ssh_bruteforce` | medium / high | T1110.001, T1110 |
| `successful_logon_after_failures` / `linux_ssh_success_after_failures` | high | T1110.001, T1078 |
| `web_auth_bruteforce` | high | T1110.001 |

Severity `high` и паттерн «успех после серии провалов с того же IP» включают
этот playbook автоматически; `medium` — по решению дежурного аналитика.

## 2. Немедленные действия (приоритет 1)

1. **Не блокировать IP сразу** — источник может быть NAT/VPN-шлюзом офиса;
   блокировка без данных отрежет легитимных пользователей.
2. Зафиксировать в тикете: IP, учётные записи, first/last seen, число попыток.
3. Поднять приоритет сессии, не прерывая сбор телеметрии.

## 3. Триаж (первые 30 минут)

- [ ] Совпадает ли учётная запись неудачных попыток с успешным входом?
- [ ] Тип входа (Windows `logon_type` 3/10 или SSH) соответствует классу учётной записи (сервис / интерактивная)?
- [ ] Геолокация и ASN IP: хостинг/VPN-провайдер? Оттуда обычно ходит пользователь?
- [ ] Время: рабочие часы или ночной интервал? Сопоставить со сменой пользователя.
- [ ] Что происходило **после** входа: EncodedCommand, LOLBins, запуск из Temp, соединения наружу (`powershell_encoded_command`, `lolbin_execution`, `process_from_suspicious_path`, `suspicious_network_connection`)?
- [ ] Подключена ли MFA? Если да — был ли push подтверждён самим пользователем?

## 4. Матрица решений

| Наблюдение | Решение |
|---|---|
| Только провалы, без успешного входа | Усилить мониторинг учётной записи; проверить IP в threat intel; решить вопрос превентивной блокировки по процедуре |
| Провалы + успех + активные пользовательские действия | Полный разбор хоста: изоляция по утверждённой процедуре, смена пароля (шаг 5) |
| Провалы + успех + только пассивные команды (whoami, net user) | Вероятна разведка; подтвердить с владельцем учётной записи допустимость таких действий |
| MFA push подтверждён пользователем, но вход ему не принадлежит | Фишинг MFA — полноценный инцидент, немедленное реагирование |

## 5. Содержание (если компрометация подтверждена)

1. Смена пароля учётной записи, отзыв активных сессий и токенов (и Kerberos-тикетов).
2. Изоляция хоста по утверждённой процедуре — без удаления артефактов при изоляции.
3. Разбор хоста: персистентность (Run keys, scheduled tasks, services), новые локальные администраторы, боковое перемещение (4624 logon_type 3 на другие хосты).
4. Загрузить IOC (IP, хеш-суммы файлов, домены) в SIEM и прогнать корпоративный поиск по остальным хостам.
5. Документировать хронологию: каждый шаг с timestamp и ссылками на исходные события.

## 6. Обучение и follow-up

- Провести инструктаж с пользователем: парольная гигиена, антифишинговая осведомлённость.
- Обновить детекции и пороги по статистике ложных срабатываний после закрытия инцидента.
- Добавить новые индикаторы в `sigma-rules/` с указанием уровня уверенности.

## 7. Ограничения

- Playbook адаптирован под учебный датасет; реальный runbook требует согласования
  с SLA, IR-командами и правовыми требованиями организации.
